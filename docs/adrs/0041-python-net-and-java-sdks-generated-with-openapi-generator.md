# Python, .NET and Java SDKs generated with openapi-generator

## Status

Accepted. Extends [ADR 0030](0030-openapi-for-the-public-api-with-hono-openapi.md)
("SDKs are generated, never written") past TypeScript. The SDK pages are in the
developer docs ([ADR 0026](0026-astro-starlight-for-the-developer-docs-site.md)).
Behaviour is in [HTML to PDF API](../features/html-to-pdf-api.md).

## Context

Integrators outside Node want typed clients for `/api/v1`. Customers self-host
([competitive scope](../features/competitive-scope.md)), so the clients ship from
this repo and must track the document their deployment serves. Nobody here
maintains Python, C# or Java code day to day, so the clients have to be
regenerated, not edited.

The document is OpenAPI 3.1 generated from zod. Three features trip
generators: render and generate answer 200 with either PDF bytes or JSON
(picked by a body field, not `Accept`); a few parameters are `anyOf` (the
`version` path segment is a number or `latest`); and zod adds `const`
and a regex `pattern` next to `format: date-time` / `uuid`. We tried each
candidate on the real document (October 2026).

## Decision

- **[openapi-generator](https://openapi-generator.tech) 7.26, one pinned jar
  for all three languages:** `python` (pydantic v2, urllib3),
  `csharp` with the `generichost` library (System.Text.Json, `net8.0`, one
  typed response per status), and `java` with the `native` library
  (`java.net.http` + Jackson, Maven). One tool, one set of quirks.
- **A compatibility pass, not API changes.**
  [scripts/generate-sdks.ts](../../scripts/generate-sdks.ts) copies the
  document and, for generators only: turns `anyOf` parameters into a string
  (or the array branch, repeated), turns `const` into a one-value `enum`
  (dropped on booleans), and drops `pattern` where `format` already says it.
  Without it the Java and C# output doesn't compile.
- **Committed output** in [packages/sdk-python](../../packages/sdk-python),
  [packages/sdk-dotnet](../../packages/sdk-dotnet) and
  [packages/sdk-java](../../packages/sdk-java), like the TypeScript SDK, so a
  change to the API shows up as an SDK diff in review. Each package has a
  hand-written README and a smoke example; the generator writes everything
  else, without generated docs, tests or CI files.
- **`pnpm sdk:generate`** regenerates every SDK: the TypeScript one (which
  writes the document) then the three others. It needs Java 11+ to run the
  generator, and downloads the jar from Maven Central on first use.
- **PDF-or-JSON responses come back as bytes.** The generators type a 200
  by its first content type, so a JSON answer (`response: json` or
  `signing`) is parsed with the SDK's own model (`GenerationResult`,
  `SigningPackage`). The READMEs show how.

## Alternatives considered

- **Best tool per language:** [openapi-python-client](https://github.com/openapi-generators/openapi-python-client)
  (httpx, attrs) for Python, [Kiota](https://learn.microsoft.com/openapi/kiota/overview)
  for C# and Java. Nicer Python, but three tools to pin and learn. Both had
  the same PDF-or-JSON gap (openapi-python-client also needs config for
  `application/pdf`; Kiota picked JSON and dropped the PDF path). Kiota
  wraps every nullable field in a `Member1` type and needs its runtime
  packages.
- **Hand-written thin clients** over httpx, `HttpClient` and `java.net.http`:
  fewest files and best ergonomics, but they drift from the document, which
  ADR 0030 rules out.
- **Changing the API so generators cope** (separate PDF and JSON endpoints,
  plain-string `version`): the TypeScript SDK and the curl guides handle the
  current shape well; the compatibility pass costs a few lines instead.
- **Not committing output,** generating in CI only: reviewers would lose the
  diff, and there's no publishing pipeline yet anyway.

## Consequences

- Generated code is large and generic (some inline models get names like
  `RenderRequestSignersInner`). The READMEs are the entry point, not the
  sources.
- OpenAPI 3.1 support in openapi-generator is still labelled beta. A
  generator bump can change output; the smoke builds catch breakage.
- A new `anyOf` parameter, or another zod construct a generator misreads,
  may need a rule in the compatibility pass.
- Not published to PyPI, NuGet or Maven Central yet; integrators build or
  vendor from the repo. Package ids (`necodoc`, `Necodoc.Sdk`,
  `dev.necodoc:necodoc-sdk`) are placeholders until publishing is decided.
