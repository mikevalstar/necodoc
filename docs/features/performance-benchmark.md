# Performance benchmark

## Summary

`pnpm bench` starts a throwaway necodoc stack, measures how fast it renders through `/api/v1`, and writes the results as JSON plus a readable summary. The [marketing site](marketing-site.md) imports the JSON, so every performance number on the site is regenerated by a run, never typed by hand.

## Motivation

Performance claims on a website drift from the product unless they come from a script anyone can rerun. Buyers comparing PDF tools ask for latency and throughput on stated hardware; we want to answer with a reproducible method and its limits, not a best-case figure.

## Behavior

- **Isolated stack.** The run starts its own Postgres cluster in a temporary directory, from the same Postgres build as the local server (`pg_config`), creates and migrates `necodoc_bench` in it, starts one `ROLE=api` process and `ROLE=worker` processes on unused ports, and gives them a temporary storage directory. It never touches the dev database, the dev Postgres server or the dev server's port. At the end it stops every process it started and deletes the cluster, also when it fails. A private cluster rather than a database on the dev server because each process opens up to about 20 connections (its pool plus pg-boss's): eight workers don't fit in a default server's 100 alongside the dev server.
- **Seeded through the product.** The first sign-up becomes the admin; it uploads the PDF fixtures, creates and publishes the templates, and creates an API key. Measurements then use only the public API with that key, as a customer would ([HTML to PDF API](html-to-pdf-api.md)).
- **What's measured:**
  - HTML to PDF render latency: a simple one-page document, and a three-page invoice with header and footer bands.
  - Designed template generate latency: a surety bond template with conditional sections and repeating rows ([document templates](document-templates.md)).
  - Overlay generate latency on two [surety bond fixtures](../../fixtures/pdfs/surety-bonds/README.md): one with AcroForm fields, one flat PDF ([PDF overlay templates](pdf-overlay-templates.md)).
  - Batch throughput in documents per minute for a JSON batch, with 1, 2, 4 and 8 workers at a stated `RENDER_CONCURRENCY` ([render queue and batches](render-queue-batch-jobs-and-scaling.md)).
  - Cold versus warm Chromium: the first render on a freshly started worker against steady state.
  - PDF/A-2b plus PDF/UA overhead on the invoice ([archival and accessible output](archival-accessible-and-certified-output.md)); skippable.
- **Statistics.** Latency runs are sequential, one request at a time, after warm-up requests that are left out of the stats. Each scenario reports sample count, mean, min, max, p50, p95 and p99 for the client-measured round trip, and the same for the [generation log](generation-log.md)'s queue wait, worker run time and server total, plus mean Liquid, Chromium, bands, stamping and finishing times.
- **Environment.** Every result records CPU model and cores, memory, OS, Node, Chromium, Postgres, worker count and concurrency, git commit (and whether the tree was dirty), date, and the load average before the run.
- **Output.** [`scripts/bench/results/latest.json`](../../scripts/bench/results/latest.json), a timestamped copy beside it, and [`latest.md`](../../scripts/bench/results/latest.md). The JSON's shape is the zod schema in [schema.ts](../../scripts/bench/src/schema.ts) and carries a `schemaVersion`; changing its shape bumps the version so the site's import fails loudly instead of showing wrong numbers.
- **Configurable size.** Flags set samples, warm-up, batch rows, worker counts, concurrency and cold starts (`pnpm bench --help`), so a laptop run stays under about fifteen minutes and a server run can go bigger.

## How to reproduce

1. Postgres 18 binaries on PATH (`brew install postgresql@18`; `pg_config` must name them, or set `PG_BINDIR`). The local server doesn't need to be running.
2. Chromium installed (`pnpm --filter @necodoc/api chromium:install`).
3. Close heavy apps, then `pnpm bench`. `pnpm bench --quick` is a short smoke run whose numbers aren't for publishing.

The runner is [run.ts](../../scripts/bench/src/run.ts); the stack it starts is in [stack.ts](../../scripts/bench/src/stack.ts), the documents and data in [scenarios.ts](../../scripts/bench/src/scenarios.ts).

## Caveats and limits on claims

- **Hardware.** Numbers belong to the machine in the result's environment. A laptop shares its CPU with everything else running and throttles under sustained load; a server will differ in both directions. The site must state the hardware next to every number.
- **Everything is local.** Postgres runs on the same machine with default settings (except `max_connections`), storage is the local disk driver, and the client calls over loopback. No network latency, object storage (S3, Azure) round trips, TLS or reverse proxy are included.
- **Our documents, not yours.** Render time grows with page count, images, fonts and table size. The scenarios are representative insurance documents, not a worst case.
- **Batch throughput includes the queue.** It's measured from the batch's creation to its last row finishing, so it includes pg-boss pickup. Workers run on one machine and share its CPU, so the scaling curve on a laptop says little about a multi-node cluster.
- **Cold start** is a fresh worker process launching Chromium on its first job, not a container or machine cold start.
- **Synchronous latency** is one request at a time; it says nothing about latency under concurrent load.
- Claims on the site quote p50 and p95 from a full (non-`--quick`) run, with the date, hardware and commit, and link to this page.

## Findings

- **The fetch loop capped batches (fixed).** Each worker slot waited out pg-boss's 0.5 s poll after every job, so a worker did 240 docs/min at `RENDER_CONCURRENCY=2` whatever the render time, and throughput only grew by adding workers. Slots now fetch again as soon as they finish ([render queue implementation](render-queue-batch-jobs-and-scaling.md#implementation)): one worker went from 240 to about 940 docs/min with sequential latency unchanged.
- **Past that, the laptop's Chromium capacity is the ceiling.** With 2 or more workers the M5 laptop levels off at about 1,100 to 1,250 docs/min. Each render's Chromium and band time rise roughly with the number of renders running at once while Postgres shows no lock waits, so the renders compete for the machine (4 performance cores, shared with whatever else runs), not for the queue. More workers help on more cores or more machines.

## Acceptance criteria

- [ ] `pnpm bench` runs end to end on a laptop in under fifteen minutes and leaves no processes, Postgres cluster or temp files behind.
- [ ] It never connects to the dev database, the dev Postgres server or the dev server's port.
- [ ] `latest.json` validates against the schema and holds every scenario above with its sample counts and environment.
- [ ] Warm-up requests are excluded from the steady-state stats.
- [ ] `latest.md` reads as a summary someone can check the website's numbers against.
